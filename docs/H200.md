# NVIDIA H200 (SXM) — what matters for serving DeepSeek-V4.1-Flash

## Per-GPU numbers

| Resource | H200 SXM | Notes for us |
|---|---|---|
| Architecture | Hopper GH100, **SM90** (compute capability 9.0) | Same silicon as H100; only the memory changed |
| SMs | 132 | Persistent kernels / SM partitioning (e.g. reserving 20–24 SMs for DeepEP comms) matter |
| HBM | **141 GB HBM3e** | 76% more than H100-80G. Lets the ~510 GB checkpoint fit on 4 GPUs (564 GB), but with little to spare |
| HBM bandwidth | **4.8 TB/s** | Decode is bandwidth-bound: the main lever is bytes moved per generated token |
| L2 cache | 50 MB | Big enough to keep small hot tables (indexer weights, router) resident |
| Shared memory | 228 KB per SM (227 KB usable per block) | Sets tile sizes for FlashMLA-style sparse attention kernels |
| BF16 / FP16 dense | ~989 TFLOPS | |
| **FP8 dense** | **~1,979 TFLOPS** (3,958 with 2:4 sparsity) | The fastest tensor-core format on Hopper. FP8 GEMMs use `wgmma` + TMA (DeepGEMM / CUTLASS 3.x) |
| FP4 / MXFP4 / NVFP4 tensor cores | **None** | Any FP4 weight must be dequantized in-kernel (Marlin W4A16, or W4A8 → FP8 wgmma) |
| NVLink 4 | 18 links, **900 GB/s total (450 GB/s each way)** via NVSwitch | All-to-all and all-reduce between any GPU pair at full speed. Usable all-to-all bandwidth in practice is ~150–160 GB/s per GPU per direction with DeepEP normal mode |
| PCIe | Gen5 x16, ~64 GB/s per direction | Host↔device path for KV/Engram offload. ~1.5% of HBM bandwidth |
| TDP | up to 700 W | Check `nvidia-smi -q -d PERFORMANCE` for power throttling under load |

Hopper features we use, which SM100 (Blackwell) code paths don't: `wgmma` (warpgroup MMA, not `tcgen05`/UMMA), TMA, thread-block clusters + distributed shared memory, FP8 E4M3/E5M2. Blackwell-only features (TMEM, `tcgen05`, 2-SM UMMA, native FP4, NVLink 5) **are not available**. So any DeepInfer kernel built only for SM100 needs an SM90 equivalent or a port.

## 4×H200 node budget

| | Value |
|---|---|
| Total HBM | 564 GB (4 × 141) |
| Total HBM bandwidth | 19.2 TB/s |
| Total FP8 | ~7.9 PFLOPS dense |
| Intra-node interconnect | NVSwitch, full 450 GB/s/dir per GPU |

The 4-GPU constraint is the defining problem. The ~510 GB checkpoint takes about 90% of HBM, which leaves roughly **8–12 GB/GPU** for KV cache, activations, CUDA graphs and comm buffers, before any memory savings. **Throughput at this scale depends mostly on how many concurrent sequences fit**, so memory comes first. See `docs/ARCHITECTURE.md` for the plan: what to offload or compress, and why.

## Roofline intuition for decode

For a decode step with batch *B*, each GPU must stream the weights it owns once per step (if they are not already in L2). With EP=4, each GPU holds about 1/4 of the weights:

- weight bytes per GPU ≈ 128 GB → **≈ 27 ms per step at 4.8 TB/s** if every expert is touched (true for any B ≥ ~64 with top-k routing over a few hundred experts).
- so steps/s ≈ 37 and per-GPU throughput ≈ 37 × B × (1 + accepted draft tokens). **Batch size and speculative acceptance both multiply throughput directly**, and weight streaming is a fixed cost per step.

This is why the two biggest levers are: (1) free HBM so *B* can grow, and (2) multi-token speculative decoding (DSpark/MTP), which turns one weight pass into several tokens. Kernel-level gains (FP8 vs W4A16 MoE, fused attention) come next.
